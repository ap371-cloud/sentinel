# Every feature in plain language

No cryptography knowledge required. Each entry says what it does, why it exists, and — importantly —
what it does not prove.

---

### Feature: Post-quantum cryptography (ML-KEM, ML-DSA)

**What it does.** Two standards published by NIST, called ML-KEM and ML-DSA, replace the older
encryption and signature methods that a future quantum computer would break.

**Why we need it.** Documents classified today may still be readable in twenty years. If the encryption
is broken by then, the classification was meaningless. Using these now means the material stays
protected for its whole lifetime.

**What it does NOT prove.** That the computer running it is free from malware, that the keys are
genuinely secret, or that the software has been independently audited. Those are separate problems.

---

### Feature: AES-256-GCM document encryption

**What it does.** Scrambles the document so an unreadable copy would be useless without the key. It
also detects any change to the scrambled data.

**Why we need it.** The document must be unreadable in storage, in transit and in a backup.

**What it does NOT prove.** That the key is safe. AES is a well-understood standard; the risk lives in
key handling, not in the algorithm.

**Why not post-quantum here?** Because FIPS 203 and 204 cover key exchange and signatures. Bulk data
still uses a symmetric cipher, and that is correct. Calling AES "post-quantum" would be inaccurate.

---

### Feature: One key per recipient

**What it does.** The document is scrambled once. Each recipient receives the unlocking key sealed
separately, in a way only they can open.

**Why we need it.** This is how the same document can go to many people without everyone sharing one
key. It also means you can remove one person's access without re-encrypting for everyone else.

**What it does NOT prove.** Anything about what the recipient does after unlocking.

---

### Feature: Decryption session

**What it does.** Every successful decryption is recorded as its own session with a unique reference.

**Why we need it.** It is the unit that everything else attaches to. Without it, "who decrypted this"
has no precise answer.

**What it does NOT prove.** That the person was present. It records that a specific authorised
decryption happened once.

---

### Feature: Session-specific forensic watermark

**What it does.** The moment a document is decrypted, an invisible mark unique to that session is
added to it. Two recipients reading the same document receive copies that look identical but carry
different marks.

**Why we need it.** When a copy appears outside the authorised group, the mark identifies which
session produced it.

**How it works.** A number is computed from the recipient, document, document fingerprint, session and
a one-time random value. That number is scrambled using a secret key held inside the system, so the
mark reveals nothing readable. It is then written into the page image using a technique that spreads it
across thousands of small changes, which is why it survives saving, compression and resizing.

**What it does NOT prove.** That the person leaked the file. It proves a specific decryption session is
cryptographically linked to the copy. It does not survive being photographed at an angle, heavily
cropped, or regenerated by an image tool — and the system reports that honestly rather than guessing.

---

### Feature: Blind extraction

**What it does.** Investigators can recover the mark from a leaked file **without having the original
document** to compare against.

**Why we need it.** The original may be unavailable, or the leaked copy may have been edited — which
means their hashes will never match. Because the mark is keyed to the document's identity rather than
to the file's contents, recovery still works.

**What it does NOT prove.** That the copy is unaltered. That check happens separately.

---

### Feature: Confidence score

**What it does.** Reports how strongly the mark was recovered, measured as signal strength compared with
the page's own noise.

**Why we need it.** A recovered mark with a weak signal is a lead, not a conclusion. The system
reports `FOUND`, `WEAK MATCH`, `CORRUPTED` or `NOT FOUND` and never displays 100%.

**What it does NOT prove.** Any absolute certainty. It is capped below certainty on purpose.

---

### Feature: Hash

**What it does.** Produces a short fixed-length fingerprint of a file. Change one character and the
fingerprint changes completely.

**Why we need it.** It is how the system proves a file is the same one it recorded, and how a chain of
records is linked so any alteration is visible.

**What it does NOT prove.** Who created the file, or when.

---

### Feature: Digital signature (ML-DSA)

**What it does.** Creates a mark that only the holder of a specific private key can produce, and which
anyone can check using the matching public key.

**Why we need it.** It is what stops the system, or its administrator, from making up a decryption
record. A record signed with the service's own key instead of the recipient's fails verification, and
the attack laboratory demonstrates exactly that.

**What it does NOT prove.** That a human authorised it. A key can be used by malware on a compromised
machine.

---

### Feature: Content hash inside the signature

**What it does.** Includes the mark itself in the signed record.

**Why we need it.** Without this, a recipient could argue the fingerprint was added after they signed,
which would undermine the entire attribution.

**What it does NOT prove.** Anything beyond binding these facts together at one moment.

---

### Feature: Merkle tree

**What it does.** Combines many transaction fingerprints into one summary value, and can produce a
short "receipt" proving one specific transaction is included in that summary.

**Why we need it.** It lets an investigator confirm a specific transaction was genuinely committed,
using only the summary and the receipt — without having to trust the node that stored it.

**What it does NOT prove.** That the transaction was legitimate. It proves inclusion, not correctness.

---

### Feature: Permissioned ledger

**What it does.** An append-only record shared across several independent local copies. Each entry
carries a link to the previous one and a quorum of digital signatures.

**Why we need it.** A log kept in one place can be edited by whoever controls that place. Agreement
between independent copies means altering one is detectable.

**What it does NOT prove.** That the entries are true. It proves they have not been altered since they
were written, and by whom they were authorised.

---

### Feature: Quorum certificate

**What it does.** Requires signatures from a majority of nodes before an entry is written.

**Why we need it.** One compromised or faulty node cannot unilaterally add or alter history.

**What it does NOT prove.** That a majority of nodes are honest. In a fixed, known node set that is an
operational assumption, stated as such in `docs/LEDGER.md`.

---

### Feature: Device binding

**What it does.** Refuses decryption requests from devices that are not registered to the recipient.

**Why we need it.** Stolen credentials used from a new machine are a common pattern.

**What it does NOT prove.** That the device is uncompromised. The fingerprint is asserted by the
client, not attested by hardware. Production requires TPM-backed device identity.

---

### Feature: Two-person control

**What it does.** For sensitive actions, requires one person to request and a **different** person to
approve. The requester can never be the approver, and each approval can be used only once.

**Why we need it.** It removes the single point of failure where one account can do something
irreversible on its own.

**What it does NOT prove.** That the two people are independent in any deeper sense. It is a control
against unilateral action, not collusion.

---

### Feature: Emergency access ("break-glass")

**What it does.** Lets a recipient reach a document during an emergency when normal authorisation is
unavailable — but only with a written reason and two separate approvals. The access is watermarked and
signed like any other, and it is permanently flagged for review afterwards.

**Why we need it.** Real emergencies must not be blocked by process, but they must leave a trace.

**What it does NOT prove.** That the emergency was genuine. That judgement is made by a human
afterwards, which is why the review is mandatory.

---

### Feature: Revocation

**What it does.** Cancels an identity, a device or a key immediately. Past records are kept.

**Why we need it.** When someone leaves, is compromised, or loses a device, access must stop now —
without destroying the record of what they legitimately did earlier.

**What it does NOT prove.** That the person did nothing wrong before revocation, or that a copy
obtained earlier is no longer in circulation.

---

### Feature: Emergency lockdown

**What it does.** A senior officer can block all new sensitive operations while an incident is assessed.
Releasing it also needs two people.

**Why we need it.** When something is wrong, the priority is stopping further exposure, not
convenience.

**What it does NOT prove.** That the cause is understood. And it explicitly does **not** delete
anything.

---

### Feature: Air-gapped operation

**What it does.** Refuses every network connection except the local terminal. The refusal is enforced
at runtime and recorded, not merely documented.

**Why we need it.** In an isolated environment, software that can reach the internet eventually will.
Enforcement is the only version of "offline" that means something.

**What it does NOT prove.** That the machine has no other network path.

---

### Feature: Anomaly detection

**What it does.** Compares activity against explicit, readable thresholds — for example, more than five
document opens in a minute — and raises an alert when a threshold is crossed.

**Why we need it.** Patterns of behaviour often reveal compromise before an individual action does.

**What it does NOT prove.** That the person is guilty. The alert means "ask why".

---

### Feature: Hash-chained audit trail

**What it does.** Records every privileged action, with each entry cryptographically linked to the one
before it.

**Why we need it.** An administrator who can delete log entries is not accountable. Linking the entries
makes deletion detectable.

**What it does NOT prove.** That the underlying action was appropriate. It proves the action is on the
record.

---

### Feature: Optional local AI

**What it does.** Turns verified security data into readable briefings.

**Why it exists.** A commander needs to understand what happened without reading cryptography.

**What it does NOT prove.** Anything at all about security decisions. It has no authority to
authenticate, authorise, verify or conclude, and every output is labelled as assistance. If it is
unavailable, nothing changes.

---

### Feature: Evidence chain

**What it does.** Shows every link from a leaked file to its decryption session, with each link
individually verified and the failing link named.

**Why we need it.** A conclusion is only as good as its weakest step. Showing the steps makes the
conclusion reviewable — and makes partial verification visible instead of hidden.

**What it does NOT prove.** That the evidence tells the whole story. It proves the links it can reach.
