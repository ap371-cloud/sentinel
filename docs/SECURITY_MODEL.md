# Security model

## 1. Principle

**Never trust — always verify.** Authentication is not authorisation. A logged-in administrator is not
automatically trusted. A registered device is not trusted forever. A connected ledger node is not
trusted. Every sensitive action is re-evaluated from live state.

Nothing is cached across requests for the purpose of an access decision. That is why a revocation
takes effect on the very next call rather than when a token happens to expire.

---

## 2. What the system protects

| Asset | Against whom | Primary control |
|---|---|---|
| Document content | Network observer, storage reader | AES-256-GCM with the hash bound as associated data |
| Content key | Other recipients | ML-KEM-768 key establishment per recipient |
| Attribution record | Compromised service, malicious administrator | ML-DSA-65 signature under the recipient's key |
| Ledger history | Privileged insider, database editor | Replication, quorum certificates, append-only storage guards |
| Audit history | Same | Separate hash chain, anchored into the ledger |
| Watermark derivation | Attacker holding a leaked copy | HMAC under a vault-held root secret |
| Authorisation decisions | Any single privileged account | Separation of duties and two-person control |

---

## 3. Zero trust

```
IDENTITY + ROLE + CLEARANCE + UNIT + NEED-TO-KNOW + DOCUMENT POLICY +
DEVICE TRUST + KEY STATUS + SESSION STATUS + DOCUMENT STATE + TIME POLICY +
REVOCATION + SYSTEM SECURITY STATE  →  ALLOW | DENY | REQUIRE_SECOND_APPROVAL
```

Fourteen checks run in a fixed order and each returns a reason code. The engine is a pure function of
its inputs, which is what makes it directly testable — see `tests/test_authorization.py`, where every
control has a negative test.

**Need-to-know is enforced above clearance.** A recipient holding TOP_SECRET clearance is still refused
a document they are not assigned to. That case is in the demonstration because it is the one most
systems get wrong.

---

## 4. RBAC and separation of duties

| Role | Can | Cannot |
|---|---|---|
| COMMANDER | Command view, approve, lockdown, incident ownership | Upload documents, administer identities |
| SECURITY_OFFICER | Revoke identities/devices/keys, approve, lockdown | Upload documents, run forensic analysis |
| DOCUMENT_ADMIN | Manage identities, devices, documents, policy | **Approve, analyse evidence, write to the ledger, own incidents** |
| SENDER | Upload, seal, version, grant | Decrypt, approve, analyse |
| RECIPIENT | Read documents, decrypt | Anything administrative |
| INVESTIGATOR | Analyse leaks, manage cases, export with approval | Modify policy or ledger, approve |
| LEDGER_OPERATOR | Verify and administer nodes | Analyse evidence, manage identities |
| AUDITOR | Verify everything | Modify anything |

The load-bearing property: **DOCUMENT_ADMIN holds no evidence, ledger-write, approval or incident
authority.** A compromised administrator can create accounts and change configuration, but cannot
forge attribution, rewrite history, or approve its own request. That is asserted in
`tests/test_authorization.py::TestRolePermissions`.

Read-only enforcement is structural, not per-route: `require_writable` refuses read-only roles before
any handler body runs.

## 5. Cryptography

### 5.1 Post-quantum primitives

| Purpose | Algorithm | Status |
|---|---|---|
| Key establishment | ML-KEM-768 (FIPS 203) | Real, via `pqcrypto` 1.0.0 |
| Signatures | ML-DSA-65 (FIPS 204) | Real, via `pqcrypto` 1.0.0 |
| Bulk content | AES-256-GCM | Real, via `cryptography` |

Document content uses AES-256-GCM, and that is the correct choice. FIPS 203 and FIPS 204 standardise
key establishment and signatures; bulk authenticated encryption remains a symmetric AEAD. **Labelling
AES as post-quantum would be wrong**, and the documentation says so explicitly.

Domain separation contexts (`CTX_DECRYPTION_EVENT`, `CTX_LEDGER_BLOCK`, `CTX_LEDGER_VOTE`,
`CTX_SESSION_ATTESTATION`) are authenticated into every signature, so a decryption signature cannot be
replayed as a ledger block or a vote. There is a test for it.

### 5.2 Key management

- Private keys are generated by the post-quantum keygen, never by hand-written code.
- They are encrypted at rest with AES-256-GCM under a scrypt-derived key-encryption key.
- They are never returned by the API, never stored in the operational database, and never logged.
  `public_metadata()` structurally omits secret fields.
- Signing and decapsulation need the raw key inside the process, so `signing_secret_for()` is exposed
  deliberately and narrowly. Every call site is inside the trusted boundary.

> **Development abstraction.** The key-encryption key comes from a local file by default. An attacker
> with the machine gets the keys. Production requires HSM or TPM-backed, non-exportable keys — see
> `docs/PRODUCTION_GAPS.md`.

### 5.3 Canonical serialisation

Signing and hashing both depend on one byte-exact serialisation: sorted keys, fixed separators, ASCII.
A test asserts that key ordering and nesting do not change the bytes. Without this, two correct
implementations would produce different signatures for the same event.

## 6. Non-repudiation, and its exact limit

The recipient signs a payload containing the document, version, hash, device, session, timestamp and
**the watermark tag**. That last field matters: without it a recipient could argue the fingerprint was
added afterwards.

What this gives: a record that only the holder of the recipient's private key could have produced, and
which no service key can substitute. `tests/test_cryptography.py` and the attack laboratory both
demonstrate that a service-key forgery fails verification.

What this does not give: proof that a human was at the keyboard. A compromised endpoint can complete
the entire flow on the user's behalf with the user's key.

---

## 7. Watermark security

- **Opaque.** HMAC-SHA256 over canonical inputs, truncated to 64 bits. No readable identity.
- **Session-specific.** Session id and a fresh nonce are inside the derivation.
- **Keyed.** Carriers derive from a vault-held root secret. An attacker holding a leaked copy cannot
  compute them, so they cannot strip the mark by re-encoding with knowledge of the pattern.
- **Redundant.** 512 independent carriers per bit; the bit value rides on the correlation sign, so a
  zero bit is an inverted excursion rather than an absent one.
- **Honest.** Confidence is measured from the within-bit noise floor, capped below 1.0, and reported
  as `FOUND`, `WEAK MATCH`, `CORRUPTED` or `NOT FOUND`. A missing mark is a legitimate result.

**Known weakness, stated plainly:** two recipients who collude can difference their copies to estimate
the embedding pattern. Collusion-resistant watermarking is a separate research problem and is not
implemented here. It is listed in the threat model.

## 8. Ledger integrity

Hash chaining alone would not satisfy "no single administrator can alter the record", because an
administrator with database access can edit a row and recompute its hash. Four layers address that:

1. **Separate replicas.** Each node owns its own database file. One file is not the whole ledger.
2. **Quorum certificates.** A block is written only with signed votes from a quorum of distinct nodes.
3. **Recomputed verification.** Verification rebuilds the Merkle root from stored transactions and
   checks signatures against registered public keys — not just the stored block hash.
4. **Cross-node state roots.** A running commitment to chain history. Two nodes at the same height with
   different state roots are provably not looking at the same ledger.

Additionally, security-bearing columns are protected by SQLite triggers scoped to those columns, so
updating a block hash, a signature or an evidence hash from outside the application is refused at the
storage layer. The attack laboratory demonstrates both halves: the guard refuses the first write, and
after the guard is removed, replication-based detection catches the change.

The audit chain is separate from the ledger on purpose: an operator who compromises the ledger service
still cannot forge the administrative history without breaking that chain.

---

## 9. Replay protection

Every decryption requires a server-issued nonce bound to the identity and document, with a short
expiry. It is consumed on first use. A second presentation raises `REPLAY_ATTACK_DETECTED`, raises a
security event, and names the reason. A nonce issued to a different identity is refused the same way.

This makes a captured request useless for obtaining a second authorised decryption.

---

## 10. Operational controls

**Emergency lockdown** blocks new sensitive decryptions, flags active sessions and creates a signed
incident. It never deletes evidence and never creates a hidden bypass. Releasing it also requires two
people, so an attacker who manages to engage a lockdown cannot quietly release it.

**Break-glass access** requires a written justification and two distinct approvers. The resulting
decryption is watermarked and signed like any other, and the event is flagged for mandatory post-event
review. There is no administrator override anywhere in the codebase.

**Revocation** is immediate and cascading: an identity, a device or a key. Historical records are
never removed; the revocation register is itself append-only.

**Key compromise workflow:** revoke key → revoke associated devices → block new sessions → flag related
activity → create an incident. Events already signed by that key remain valid evidence, and the
limitation of relying on a revoked key is recorded.

---

## 11. Local AI boundary

The model may summarise incidents, explain anomaly triggers, cluster events and draft briefings. It
may not authenticate, authorise, verify signatures or proofs, decide revocation, or produce a forensic
verdict.

It receives aggregated, already-verified metadata — never plaintext document content. Output is always
labelled `AI-ASSISTED ANALYSIS`. If the service is unavailable the platform reports `AI SERVICE
OFFLINE` and every deterministic function is unchanged.

---

## 12. What this system does not protect against

Stated plainly, because a security document that only lists strengths is not a security document.

1. **A compromised endpoint.** No software control stops a user photographing, screenshotting or
   transcribing displayed content.
2. **A colluding pair of recipients.** They can difference their copies to estimate the mark.
3. **An attacker who replaces the whole host.** The key vault file is only as protected as the machine.
4. **Physical security.** Paper copies, screen photography and cameras are out of scope.
5. **Coerced recipients.** A legitimate user with a legitimate key can decrypt under duress.
6. **Statistical attacks on the tag.** The tag is 64 bits, which is ample against guessing but not a
   research-grade watermarking construction.
7. **Denial of service.** Nothing stops an authorised user flooding the ledger.
8. **Social engineering.** A commander can still be persuaded to approve something unwise.
9. **Certification.** This system is not accredited for any classification of information.

Items 1 and 9 are the two that matter most, and both are restated in the UI and in every evidence
report.
